# scripts — перенос изменений между машинами

Одна папка в корне с проектами (дома — `~/projects/scripts`, на работе — рядом с сервисами)
вместо копий `git-copy.sh` / `git-apply.sh` / `project-copy.sh` / `project-apply.sh` в каждом проекте.

Нужен только Python 3.6+ и git, сторонние пакеты не используются. Проекты — все каталоги в том же корне,
где лежит `scripts/`.

## Быстрый старт

```bash
./ui.sh            # веб-интерфейс на http://127.0.0.1:8765 (браузер откроется сам)
```

**Копировать** — выберите проект, затем что выгрузить:
- **Последний коммит** выбранной ветки;
- **Коммиты** — отметьте нужные в таблице (Shift+клик выделяет диапазон), клик по строке показывает файлы коммита.
  Если между отмеченными коммитами есть неотмеченные, которые меняли те же файлы, предпросмотр об этом предупредит:
  в выгрузку попадает полное содержимое файла, а значит и их правки;
- **Весь проект** — снимок всех файлов, которые видит git (или всех, кроме мусора сборки, если git нет).
  Для проекта в git к снимку добавляется история: изменения последних N коммитов текущей ветки (по умолчанию 10,
  поле «История» или `history_commits` в настройках; 0 — без истории).

Выгрузка режется на части не длиннее 7000 строк. У каждой части есть кнопка «Копировать» — копируйте
части по очереди и вставляйте на другой машине.

**Применить** — вставьте текст в поле и нажмите «В inbox» (части можно вставлять по одной и в любом порядке)
или положите файлы в папку `inbox/` под любыми именами. Пакет, в котором есть все части и сошлась контрольная сумма,
получает статус «готов». Дальше: «Предпросмотр» показывает, что будет создано, изменено и удалено, а «Применить»
вносит изменения.
- Если проекта нет, а применяется снимок, проект создаётся, выполняется `git init` (на той же ветке) и коммиты:
  история из снимка или один стартовый коммит.
- Снимок к существующему проекту в git по умолчанию применяется в новую ветку: флажок «Отвести ветку» и имя
  (запоминается) — ветка `<имя>-ДД-ММ-ГГ` отводится от текущего HEAD, HEAD переключается на неё. Если такая
  ветка уже есть, добавляется `-2`, `-3`… В ветку записываются:
  1. «Импорт …: состояние на …» — разница между проектом и источником перед первым коммитом истории
     (не создаётся, если проект уже в этом состоянии);
  2. коммиты истории с исходными авторами, датами и сообщениями (хеши новые). Коммиты, которые в проекте уже есть
     (дерево HEAD совпадает с деревом одного из них), пропускаются;
  3. «Импорт …: незакоммиченные изменения» — если в источнике были незакоммиченные правки.

  Рабочий каталог после применения совпадает со снимком, `git status` чистый. Бинарные файлы (без
  «Переносить бинарные файлы»), настройки IDE и защищённые файлы в воссозданной истории не меняются.
- Перед изменением существующего проекта делается бэкап затронутых файлов. Откатить применение можно во вкладке «История».
  Откатываются файлы, а если применение отвело ветку — HEAD возвращается на прежнюю ветку (сама ветка остаётся,
  удалить: `git branch -D <ветка>`). Коммит, созданный флажком «Закоммитить», остаётся в git.
- Флажок «Закоммитить после применения» (без новой ветки) коммитит только применённые файлы в текущую ветку.
  Для выгрузки коммитов каждый перенесённый коммит становится отдельным коммитом с исходным сообщением, автором
  и датой автора (коммиттер — вы, как при cherry-pick); коммиты, правки которых в проекте уже есть, пропускаются.
  Выгрузки старых версий скриптов коммитятся одним коммитом с сообщением из перенесённых коммитов.

## Командная строка

```bash
./git-copy.sh <проект>                        # последний коммит (HEAD)
./git-copy.sh <проект> 155af7c 5243d71        # несколько коммитов
./git-copy.sh <проект> HEAD~3..HEAD           # диапазон
./git-copy.sh <проект> main..feature/x        # все коммиты ветки, которых нет в main
./project-copy.sh <проект> [--with-binaries]  # снимок целиком (+ история последних 10 коммитов)
./project-copy.sh <проект> --history 30       # история последних 30 коммитов (0 — без истории)

./inbox.sh                                    # что лежит во входящих
./git-apply.sh [--project X] [--dry-run] [--commit] [файлы…]
./project-apply.sh [--project X] [--dry-run] [--force] [--commit] [--no-git] [--branch ИМЯ] [файлы…]
                                              # --branch: ветка ИМЯ-ДД-ММ-ГГ с историей из снимка

./scripts.py backups [проект]                 # бэкапы применений
./scripts.py restore <id>                     # откат
./scripts.py --help
```

Если файлы не переданы, apply берёт единственный готовый пакет подходящего вида из `inbox/`. Если таких пакетов несколько,
выводится список с ключами, и нужный пакет выбирается через `--key`.

Выгрузки пишутся в `export/<проект>/`. Прежний комплект того же вида при этом удаляется.

## Форматы

Каждая часть начинается со строки-заголовка:

```
#@transfer v1 kind=changes project=teg-reactive id=2026-09-25_14-00-00-a1b2 part=1/3 lines=6999 sha256=…
```

- `kind=changes` — формат `changed_classes.txt` (блоки `FILE:` и секция `DELETED FILES`), перед блоками идут
  `#`-строки метаданных: коммиты, исполняемые файлы, окончания строк, пропущенные файлы и `COMMIT-DATA` —
  автор, сообщение и изменённые пути каждого коммита. Если файл меняли несколько выбранных коммитов, его
  промежуточные версии идут блоками `VERSION: <коммит> <путь>` перед блоками `FILE:`. Выгрузку из одной части
  применяет и старый `git-apply.sh`: строки до первого блока `FILE:` (в том числе блоки `VERSION`) он пропускает.
  Бинарные файлы, симлинки и подмодули в выгрузку коммитов не попадают, о них выводится предупреждение.
- `kind=snapshot` — base64 от tar.gz: `manifest.txt` (`FORMAT 2`) и `files/`. Права файлов и симлинки сохраняются.
  Бинарные файлы по умолчанию не переносятся (KEEP) и при применении не удаляются. История (если есть):
  `history.json` (коммиты: автор, коммиттер, даты, сообщение) и `history/*.patch` — `git diff --binary` каждого
  коммита относительно первого родителя и `worktree.patch` с незакоммиченными правками. Старые версии скриптов
  и `bootstrap.py` эти файлы пропускают.

Старые выгрузки без заголовков тоже читаются: `changed_classes.txt` и `project-copy-<время>-part-NNN.txt`.
Проект для них нужно указать вручную. Формат 1 (`part_*.txt`) не поддерживается.

При применении снимка к существующему проекту удаляются файлы, которых в снимке нет. Исключения: KEEP,
`.idea`, `*.iml`, `.vscode`, `.claude/settings.local.json`, `CLAUDE.local.md`. Если удалять предстоит больше
`max(20, файлов_в_снимке/5)` файлов, применение останавливается: скорее всего, выбран не тот проект. Продолжить можно с `--force`.

## Первый перенос на рабочую машину

Старые скрипты новые части не читают, поэтому сама папка `scripts` в первый раз переносится стандартными утилитами.
Дома:

```bash
./project-copy.sh scripts
```

На работе вставьте части в `scripts/export/project.txt` (все подряд, в любом порядке), перенесите текстом
`bootstrap.py` в `scripts/` и выполните в каталоге `scripts`:

```bash
python3 bootstrap.py            # части в отдельных файлах: python3 bootstrap.py part-1.txt part-2.txt
```

Скрипт проверит, что части полные и контрольная сумма сошлась, распакует файлы с правами и, если каталог
ещё не в git, сделает `git init` на ветке из снимка и стартовый коммит (`--no-git` — без этого).
Лишние файлы в каталоге не удаляются.

Дальше `scripts` обновляется как обычный проект: он лежит в корне и виден в списке проектов.

## Настройки

`config.json` — общие значения. `config.local.json` — настройки конкретной машины, в git не попадает:

```json
{
  "projects_root": null,
  "max_lines": 7000,
  "port": 8765,
  "hidden_projects": ["untitled folder"],
  "aliases": {"teg-reactive": "sberhelp-teg-reactive"},
  "keep_backups": 30,
  "history_commits": 10
}
```

- `projects_root` — корень проектов (по умолчанию — родительский каталог `scripts/`);
- `aliases` — если на машинах проект называется по-разному: имя в выгрузке → локальное имя;
- `history_commits` — сколько последних коммитов добавлять в снимок проекта (0 — без истории);
- переменные окружения `TRANSFER_PROJECTS_ROOT`, `TRANSFER_DATA_DIR`, `TRANSFER_MAX_LINES` перекрывают файлы настроек
  (удобно для проверки на копиях проектов).

Веб-интерфейс слушает только 127.0.0.1. Каждый запрос к API проверяется по токену, который генерируется при запуске.
Для работы по ssh: `./ui.sh --no-browser` и `ssh -L 8765:127.0.0.1:8765 …`.
